# 模块说明 · 后端服务（server/）

> 版本：v0.3（压测与重构版）
> 变更摘要：由「单文件路由承担四种职责」重构为**分层结构**；新增关键事件 Hook；
> 新增 `GET /healthz`；限流与请求日志环境变量化；列表接口新增可选分页参数；
> 导出改为流式写出；SQLite 连接加固。

## 一、模块职责

后端服务是**唯一数据持久化与业务校验**出口。它在副机上以 Node.js 进程运行，负责：

- 托管前端静态资源（`user.html` / `admin.html` / `assets/`）；
- 提供报名相关 REST API（提交、查询、列表、导出、场次字典、健康检查）；
- 以 **SQLite 单文件**持久化报名数据（WAL 模式，重启不丢）；
- 承担**服务端二次校验**（前端校验可被绕过，唯一性与必填以服务端为准）；
- 在关键事件上执行**保护性 Hook**（报名突发 → 拦截 + 冷却 + 结构化日志）。

约定：**前端不直接接触数据库，一切读写经 HTTP API**。

## 二、分层结构与职责边界

```
server/
├── server.js                       # 进程入口：初始化 DB / Hook / App，监听端口，优雅退出
├── app.js                          # 应用装配：中间件、路由挂载、静态托管、404、错误处理
├── config.js                       # 集中配置（字典 / 错误码 / 开关 / 路径 / 版本）
├── hooks/
│   ├── index.js                    # Hook 注册与编排（按注册顺序执行）
│   └── signupBurstGuard.js         # 关键事件：在途并发提交超阈值 → 拦截 + 冷却 + 日志
├── db/
│   └── index.js                    # 连接、WAL、busy_timeout、synchronous、建表、启动备份
├── lib/                            # 纯函数层：零 IO，可被单测直接覆盖
│   ├── response.js                 # send()：统一响应体 { code, message, data }
│   ├── validate.js                 # validateSignup / buildFilters / escapeLike / parsePagination
│   ├── csv.js                      # CSV 表头、单元格转义、行格式化、BOM/CRLF 常量
│   ├── datetime.js                 # pad / todayStamp / formatDateTime
│   └── regno.js                    # 报名编号纯函数：regNoPrefix / nextRegNoFrom
├── repositories/
│   └── registrationsRepo.js        # 全部 SQL；预处理语句按 SQL 文本缓存（禁止每请求 prepare）
├── services/
│   └── registrationsService.js     # 业务编排：校验 → 查重 → 事务插入；返回结果描述对象
└── routes/
    ├── registrations.js            # 仅 HTTP 编排（薄），负责取参、调用 Hook/Service、写响应
    └── sessions.js                 # 场次字典
```

**依赖方向（单向，禁止回环）**：

```
routes → services → repositories → db
   ↘         ↘            ↘
        lib（纯函数，被各层共用）
   hooks（被 routes 调用；自身不依赖 service/repo）
```

分层理由：重构前 `routes/registrations.js` 单文件同时承担「参数校验 + SQL + CSV 拼装 + HTTP 编排」
四种职责，无法对任一职责单独测试。拆开后：

- `lib/*` 纯函数 → 单测直接覆盖，不需要起服务；
- `repositories/*` → 单测用临时库验证 SQL 行为（唯一约束、筛选、分页、编号边界）；
- `services/*` → 编排逻辑与 HTTP 解耦，返回结果描述对象而非直接写响应；
- `routes/*` → 只做「取参 → 调 Hook → 调 Service → 写响应」，保持薄。

## 三、运行方式

```bash
cd server && npm install && npm start
```

> 仓库根另有一套工程命令（`npm run lint` / `npm test` / `npm run build`），见根 `README.md`。

## 四、环境变量

| 变量 | 默认值 | 说明 |
|---|---|---|
| `PORT` | `3000` | 监听端口 |
| `DATA_DIR` | `<项目根>/data` | 数据目录（DB 与备份的默认落点） |
| `DB_PATH` | `<DATA_DIR>/app.db` | SQLite 文件路径 |
| `BACKUP_DIR` | `<DATA_DIR>/backups` | 启动备份目录 |
| `CORS_ORIGIN` | `*` | 允许来源（生产建议收紧） |
| `RATE_WINDOW_MS` | `60000` | 限流窗口 |
| `RATE_MAX` | `120` | 单窗口单 IP 最大请求数 |
| `RATE_DISABLED` | 未设置 | `=1` 时**整体关闭限流**（仅供压测，避免 429 截断结论） |
| `LOG_REQUESTS` | 开启 | `=0` 关闭请求日志（压测时关闭可显著降低同步写 stdout 开销） |
| `LOG_SLOW_MS` | `0` | 大于 0 时只记录耗时超过该阈值的请求；`0` 为全量记录 |
| `HOOK_SIGNUP_BURST_ENABLED` | 开启 | `=0` 关闭报名突发保护 Hook |
| `HOOK_SIGNUP_BURST_THRESHOLD` | `100` | 在途并发提交数阈值 |
| `HOOK_SIGNUP_BURST_COOLDOWN_MS` | `60000` | 触发后的冷却时长 |

## 五、数据模型（表 `registrations`）

| 字段 | 类型 | 必填 | 约束 |
|---|---|---|---|
| `id` | INTEGER | 是 | 主键自增 |
| `reg_no` | TEXT | 是 | 报名编号，唯一，`REG + YYYYMMDD + 4 位当日流水` |
| `name` | TEXT | 是 | 非空 |
| `role` | TEXT | 否 | `teacher` / `student` / `other`，可空 |
| `department` | TEXT | 否 | 可空 |
| `phone` | TEXT | 是 | 11 位数字；**UNIQUE 唯一索引** |
| `session` | TEXT | 是 | `morning` / `afternoon` |
| `created_at` | TEXT | 是 | ISO 时间，系统生成 |

**连接加固（v0.3 新增）**：

- `journal_mode = WAL`：提升读写并发表现；
- `busy_timeout = 5000`：写锁竞争时最多等待 5s 再报错，避免瞬时并发直接抛 `SQLITE_BUSY`；
- `synchronous = NORMAL`：WAL 模式下安全且显著降低每次提交的 fsync 开销；
- **关闭前 `wal_checkpoint(TRUNCATE)`**：把 WAL 增量合并回主库并截断，避免遗留大 WAL 文件。

**编号上限（R9 显式固定的边界事实）**：流水为 4 位补零，**单日超过 9999 条时序号自动变为 5 位**
（`REGYYYYMMDD10000`）。生成逻辑与 v0.2 完全一致（遵守 Q4 向后兼容），本版仅在测试与文档中
把该边界固定下来，避免成为隐性坑。

**编号取最大值的排序规则（基线压测实测复现的缺陷，已修）**：取当日最大编号必须按**流水数值**比较，
不能按整串字典序。流水由 4 位进位为 5 位后，字典序会把 `REG202610069999` 判为大于 `REG2026100610000`
（第 11 位 `9` > `1`），导致单日第 10000 条起永远推导出同一个编号 → 撞 `reg_no` 唯一约束 → 写入全量失败。
现固定为 `ORDER BY LENGTH(reg_no) DESC, reg_no DESC`（位数多者数值必大，同长度内字典序即数值序），
并有单测锁死该行为。

## 六、API 契约

统一响应体 `{ code, message, data }`，`code = 0` 表示成功。

| 方法 | 路径 | 说明 | 入参 | 出参 |
|---|---|---|---|---|
| POST | `/api/registrations` | 提交报名 | name, role?, department?, phone, session | 成功返回记录（含 `reg_no`） |
| GET | `/api/registrations/lookup` | 按手机号查询 | phone | 命中返回记录，未命中 `data=null` |
| GET | `/api/registrations` | 名单列表（筛选） | role?, session?, keyword?, **limit?, offset?** | 记录数组 |
| GET | `/api/registrations/export` | 导出 CSV | role?, session?, keyword? | CSV 文件流（流式写出） |
| GET | `/api/sessions` | 场次字典 | —— | 场次数组 |
| GET | `/healthz` | 健康检查（**不入 `/api`，不受限流**） | —— | `{ status, uptime, version }` |

错误码：

| code | 含义 | HTTP 状态 |
|---|---|---|
| 0 | 成功 | 200 |
| 1001 | 参数校验失败 | 400 |
| 1002 | 手机号重复 | 409 |
| **1003** | **报名突发保护触发（冷却中）** | **503** |
| 5000 | 服务器内部错误 | 500 |

> **向后兼容承诺（Q4）**：v0.2 的 5 个接口路径、请求参数、响应结构、错误码语义**全部不变**。
> v0.3 只做两件事：**新增可选参数**（`limit` / `offset`）与**新增接口**（`/healthz`）。

### 6.1 分页参数语义（R3）

- `limit` / `offset` **均可选**；**都不传时返回全量，与 v0.2 行为完全一致**；
- 传入时：`limit` 取 `1..1000`（超出即夹紧），`offset` 取 `>=0`；非法值一律按「未传」处理（不报错）；
- 非法值不报错是刻意选择：避免给既有调用方引入新的失败分支。

### 6.2 健康检查语义（R7）

- 返回 `{ status, uptime, version }`；
- 同时做一次 **DB 可写探测**：`BEGIN IMMEDIATE; COMMIT;` —— 立即申请写锁即可证明库可写，且不改动任何数据；
- 可写 → HTTP 200 `status=ok`；不可写 → HTTP 503 `status=degraded`。

## 七、业务规则（服务端实现要点）

- **R1 手机号全局唯一**：`phone` 建 UNIQUE 索引。插入命中唯一约束时**按冲突列区分**：冲突列确为
  `phone` → 返回 `code=1002`（并发兜底，与 v0.2 语义一致）；冲突列为 `reg_no` 或无法识别 → 上抛按
  `code=5000` 处理并记录日志（v0.2 把所有唯一冲突一律当 1002，曾把编号生成的故障伪装成「手机号已报名」）。
- **R2 必填校验**：仅卡姓名 / 手机号 / 场次；身份、院系可空。手机号必须 `^\d{11}$`；`role` 若填写须在字典内；`session` 必须在字典内。
- **R3 导出**：严格按当前筛选（role/session/keyword 三条件 AND）；CSV 前置 **UTF-8 BOM**，行尾 **CRLF**，表头顺序固定为
  `报名编号, 报名时间, 姓名, 身份, 院系, 手机号, 参加场次`；文件名同时给出 ASCII 与 UTF-8 编码名。
- **R4 关键字**：命中范围 = 姓名 + 手机号 + 院系（`LIKE` 包含，参数化，`ESCAPE '\'` 转义通配符）。
- **R5 流式导出**：导出不再整串拼装 CSV 后一次性 `res.send`，而是 `res.write` 逐行写出，
  消除「数据量 × 单行长度」的内存驻留；导出前后顺序（`created_at DESC, id DESC`）与内容与 v0.2 一致。

## 八、关键事件 Hook

详见 `模块说明-关键事件Hook.md`。要点：

- 语义：**在途并发提交数 > 阈值（默认 100）** → 触发冷却（默认 60s），冷却期内提交一律返回 `1003` 且**不触碰数据库**；
- 位置：**业务层**，在限流（传输层）之后执行（D13）；实现放 `hooks/`，可插拔；
- 日志：触发与恢复各输出一行 **JSON 结构化日志到 stdout**（`event=signup_burst_guard`）；
- 恢复：冷却到期后由下一个到达的请求**惰性恢复**（不使用定时器，避免持有事件循环句柄）。

## 九、安全与非功能

- **参数化 SQL**：全部使用 prepared statement，无字符串拼接，防注入。
- **预处理语句缓存**：`repositories/registrationsRepo.js` 按 SQL 文本缓存 statement（R2），
  重构前「每请求 `db.prepare()`」会产生大量 Statement 并被 GC 析构，是压测暴露的问题之一。
- **体积限制**：`express.json({ limit: '16kb' })`。
- **限流**：`express-rate-limit` 对全部 `/api/` 生效（管理端无鉴权，限流尤为必要），可用环境变量调参或整体关闭。
- **CORS**：来源由 `CORS_ORIGIN` 控制。
- **日志**：请求日志可开关、可只记慢请求；Hook 结构化日志固定写 stdout。
- **统一错误处理**：所有异常经末尾错误中间件返回 `{code:5000,...}`，不泄漏堆栈。

## 十、约束

- 仅依赖 express / better-sqlite3 / cors / express-rate-limit，**不新增任何 runtime 依赖**（Q5）；
  - **唯一例外（已获用户授权）**：`better-sqlite3` 由 `^11.3.0` **升级至 `^12.11.1`**。原因是 `npm test`
    在本机 Node v24 下随机触发原生崩溃（`Assertion failed: (env) != nullptr`，栈顶
    `Statement::scalar deleting destructor`），最小复现实验证明为 better-sqlite3 v11 的原生析构缺陷，
    同模式在 v12 下 0/15 复现，升级后 `npm test` 连跑 6 次全绿。该例外只放宽「版本号不动」，
    **依赖清单条目本身未增加**。
- `engines.node` 固定为 `>= 20`（根与 `server/` 两侧一致）：测试使用 Node 内置 `node:test` 与全局 `fetch`，
  且 `npm test` 的 glob 写法依赖 Node 20+ 的 `--test` 参数解析行为。
- 不在数据库中保存明文之外的敏感信息（本 Demo 仅姓名与手机号）；
- 管理端无鉴权为**用户明确选择**，演示结束后应关闭穿透隧道。
